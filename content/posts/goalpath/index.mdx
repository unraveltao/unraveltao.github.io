## 为什么需要一条目标路径

项目容易在四处失焦：任务不知道服务于哪个目标；已经验证的内容和下一步不清楚；失败后重复试错；工作被报告为完成，却没有可复核的证据。

GoalPath v0.1 用一条可回看的路径组织这些信息。它是待实践验证的草案，不是已经证实有效的通用方法。

## 六个概念，各管一层

- **Goal**：期望实现的能力及成功标准。
- **Milestone**：阶段性成果或关卡。
- **Path**：达成目标的候选路线，可以分支或回退。
- **Task**：能够执行并独立验收的最小工作单元。
- **Evidence**：测试输出、日志、截图或交付文件等可检查证据。
- **Decision**：说明为何继续、改道、暂停或调整目标。

GoalPath 负责“为什么、走哪条路、下一步是什么”；任务驱动流程负责“怎么执行、怎么验收”。它们互补，不需要重复维护两份任务清单。

## 一次轻量循环

1. 写清目标和验收条件。
2. 选一条主路线；只有存在真实不确定性时才列备选。
3. 把路线拆成可验收的小任务，注明输入、动作和验收证据。
4. 执行并记录实际结果，不把推测当证据。
5. 根据结果决定继续、重试、换路或暂停。
6. 更新状态，并明确唯一的下一步或阻塞原因。

状态标记：`[ ]` 表示待办或未验证，`[x]` 表示验收通过，`[-]` 表示受阻并需说明原因，`[!]` 表示失败或路线淘汰并需写明原因和下一步。后两种是 GoalPath 的文本约定，并非标准 Markdown 复选框。

## Lattice Android 试点

**目标**：验证电脑端 Agent 能否通过 ADB 执行基础 Android 操作，并为未来独立运行的手机 Agent 积累证据。

**路线**：先由电脑端 Agent 配合 ADB 验证，再评估普通 Android App 权限下能做到什么。

**当前焦点**：只读审计 `/sdcard/Download/` 中可访问文件的元数据、分类并生成报告。验收需要真实命令输出、分类统计和失败项说明；不得修改、删除或上传文件。当前状态是待执行，尚无执行证据。ADB 权限不等于普通 Android App 的权限。

候选任务包括 ADB 基础连接、下载目录只读审计、Android UI 自动化和 Agent 工具接口原型。先以这个试点连续实践 3 个任务或 2 周，再观察当前目标与下一步是否更清楚、失败是否更可追溯、无效测试是否减少，以及记录成本是否过高。达到观察周期不代表方法已验证，应根据实际记录决定是否改进。

## 单次任务复盘模板

```markdown
# GoalPath｜项目名称

## 目标
- 目标：
- 成功标准：

## 路线
- 主路线：
- 备选路线（可选）：

## 当前焦点
- 当前任务：
- 验收条件：
- 证据位置：
- 阻塞原因（如有）：
- 下一步：

## 决策记录
| 日期 | 问题 | 选择 | 原因 | 后续验证 |
|---|---|---|---|---|
```

普通任务只记录足以复核的内容；重大分歧再写详细决策。GoalPath 的 v0.1 效果仍待试点观察，之后再依据记录决定是否发布 v0.2。
