## 我为什么开始把自己的经验做成 Skill

我一开始其实没有想过要做很多 Skill。最开始接触 Skill 的时候，我只是觉得，如果 AI 经常需要按照某种固定方式完成一类事情，那是不是可以把这套东西整理出来，让它以后直接按照这个方式做。最初的理解其实很简单，有点像给 AI 写一份比较详细的说明书。

真正让我开始认真研究 Skill，是因为我自己做项目的时候，发现有很多事情一直在重复。一个项目需要 README，另一个项目又需要 README；项目需要架构说明，又需要给 Agent 看的 `AGENTS.md`；开始开发之前还需要整理需求，做完以后还要测试和验收。以前这些事情我基本都是临时去做，做到哪里算哪里。后来项目越来越复杂，我才发现，如果这些东西没有整理好，AI 也很难真正理解项目。

以前我觉得 README 就是写一个项目介绍，把项目是什么、怎么安装、怎么运行写一下就差不多了。后来实际项目做多了，我才发现，一个项目真正需要的文档可能有很多种，它们解决的问题也不一样。README 是让人快速了解项目的，架构文档是帮助理解系统怎么组成的，`AGENTS.md` 则更像是在告诉 AI 这个项目应该怎么工作、有哪些约束、哪些东西不能乱改。当这些东西越来越多的时候，我开始意识到，如果我已经花了很多时间研究“什么样的 README 才算好”，为什么以后每个项目还要重新研究一次？

于是我开始想到，能不能把这些经验留下来。这就是我开始做 Skill 的一个重要原因。

## 从一个 Skill，到一组可以组合的能力

我现在比较喜欢的一种方式，是先把能力拆成比较小的 Skill。比如 README Skill 就专门解决 README，不负责整个项目的所有事情。以后如果我又研究清楚了 `AGENTS.md` 应该怎么设计，那就再做一个专门处理 `AGENTS.md` 的 Skill；架构文档、需求文档也是一样。

这样看起来好像会产生很多 Skill，但我的想法并不是 Skill 越多越好。我更希望它们能够独立使用，同时又能够组合起来。一个项目开始的时候，可以先用需求相关的 Skill 把自己到底想做什么梳理清楚，然后用需求文档 Skill 把它记录下来，接下来再用架构相关的 Skill 思考系统应该怎么设计，开发过程中再使用 README、`AGENTS.md` 等 Skill 去维护项目文档。

最后这些东西组合起来，就不只是几个孤立的 Skill，而更像是一套帮助我开发软件的工具。

## 做 Skill 本身没有意义，真正重要的是使用

后来我又发现一个问题：如果我只是不断设计 Skill，然后给它们写很漂亮的 `SKILL.md`，最后一个都不用，那其实没有什么意义。

所以现在我越来越强调，Skill 必须进入真实任务。比如我做一个 README Skill，最好的测试并不是让我自己看一眼这个 `SKILL.md`，然后觉得“写得挺完整”，而是真的拿一个项目出来，让它重新生成 README，然后自己去看它有没有把项目讲清楚，有没有遗漏重要内容，是不是写了一堆听起来很专业、实际上没有意义的话，我自己能不能看懂。

如果它真的能让我以后少花时间写 README，那这个 Skill 才算真正有价值。

这也让我开始重新理解测试。以前我可能觉得测试主要是软件开发里面的事情，现在我发现 Skill 本身也是一种需要验证的东西。不能因为一个 Skill 的说明写得很漂亮，就认为它一定有效，它最终还是要通过真实任务来证明自己。

## Skill 也不需要永远开发下去

我现在不会要求每个 Skill 一开始就做到最终版本。比如我的磁盘管理相关 Skill，现在已经能够完成一些分析，能够帮我找到磁盘里面值得关注的东西，但后面还有测试和功能没有完全完善。如果我现在没有清理磁盘的需求，它完全可以先放在那里，标记成待完善。以后我真的需要进行磁盘治理的时候，再把它拿出来继续测试和修改。

以前的我可能会觉得，既然开始做了，就应该把它全部做完。现在我不会这么想。我做 Skill 是为了以后解决问题，而不是为了拥有越来越多的 Skill。

我现在更愿意保持一种比较简单的循环：遇到重复问题，就考虑能不能封装成 Skill；封装以后放进真实任务里使用；发现问题就修改；暂时没有需求就先停下来。等以后再次遇到类似问题，再继续。

## Skill 也开始反过来影响我自己

比较有意思的是，做到后来我发现，Skill 并不只是帮助 AI，它其实也在迫使我把自己的思考讲清楚。

以前我可能知道“一个好的 README 应该是什么样”，但让我真的把它写成规则，我反而不一定说得清楚。当我开始设计 README Skill 的时候，就不得不问自己：什么叫好的 README？它到底应该解决什么问题？哪些内容必须有？哪些内容没有必要？什么时候应该问用户？什么时候应该自己判断？什么时候应该停止？

这些问题以前可能都藏在我的脑子里，我自己也没有认真整理过。现在把它写成 Skill，就等于把自己的经验拿出来重新审视一遍。有些经验经得起验证，就留下来；有些只是以前习惯这么做，重新想一遍以后发现其实没有必要，那就删掉。

所以我现在不会把 Skill 看成单纯的提示词。它更像是我把一部分工作经验整理成一个可以重复使用、可以测试、也可以不断修改的工具。

## 我现在还不会把这套体系做得特别大

我目前反而有意识地不想无限制地做 Skill。现在真正重要的是把已经做出来的几个 Skill 拿去使用。README Skill 就真的拿项目来测试，文档相关的 Skill 就真的拿我的项目文档来跑；以后如果发现测试这些 Skill 的过程本身又有大量重复工作，再考虑是不是值得做一个测试 Skill。

我希望 Skill 的数量是被真实需求推动出来的，而不是我坐在那里想“还有什么 Skill 可以做”。如果以后我真的发现很多 Skill 都有相似的测试流程，那时候再做一个专门测试 Skill 的 Skill，我觉得就很自然，因为它是从实际问题里长出来的，而不是为了把 Skill 体系做得看起来完整，硬凑出来的。

现在回头看，我觉得自己真正想建立的可能也不是一个很庞大的 Skill 仓库。我更希望它像一个不断积累的工具箱。我学习一个东西，发现它以后会反复用到，就把它整理下来；实际使用的时候发现问题，就继续修改；最后这些东西慢慢组合起来，成为我以后开发软件时可以直接调用的一套能力。

这样的话，我现在花时间研究 Skill 才真正有意义。因为我不是在脱离开发去研究 Skill，我是在为下一次开发做准备。
